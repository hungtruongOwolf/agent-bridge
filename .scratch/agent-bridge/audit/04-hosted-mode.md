# Audit 04: Hosted mode (Unsealed and Sealed)

Date 2026-10-07. Auditor view of `architecture-v2.md` sections 3.2 (B2, B3, B5), 3.3, 3.4, 6.1, 6.3, 7.4, 10 (phases 12, 15, 16). Primary-source facts used come from the repo's own research digests (PayPal docs digest `research/09`, relay digest `research/08`, Nebius digest `research/10`); anything not confirmed there is marked UNVERIFIED. Findings are about the design text, not the code (there is none yet).

## 1. Actors and the state each holds

| Actor | Trust | Holds |
|---|---|---|
| R (requester machine) | trusted | vault, local agent, Disclosure Compiler, requester keypair, phone key(s), pinned host key (should), packet plaintext + token map |
| Ph (requester phone PWA) | trusted | phone key bound to R, approval UI |
| Hub | honest-but-curious (B2), also operates relay, escrow, quote directory, Nebius account | registry, host directory (host pubkeys), run tokens, PayPal authorization ids, ledger, Nebius account and per-task key, relay queues (ciphertext) |
| Relay (part of hub) | passive but can drop/delay/reorder/replay/swap keys | per-recipient encrypted envelopes, TTL |
| H (host operator) | untrusted, root on the box | host key, pack files (plaintext), packet plaintext, results, logs, sidecar, supervisor, detectors, receipt signing key, host clock, hub-issued Nebius key |
| A (pack author) | untrusted | pack source, share of capture; should receive nothing during run |
| Cell on H | untrusted code | sees packet plaintext under /in, model proxy socket |
| Nebius | sees prompts | per-key usage |
| PayPal | external | authorization (hold), captures, payouts |

## 2. Flow as a state machine (as written in the spec, with the missing transitions added in brackets)

Per-task state is held by the hub (authoritative for money) and mirrored by R and H. The spec never names a single authority; this audit assumes the hub should be.

States: `DRAFT -> QUOTED -> AUTHORIZED -> DISPATCHED -> ACCEPTED_BY_HOST -> RUNNING -> RESULT_READY -> DELIVERED -> {ACCEPTED -> CAPTURED -> PAID_OUT | REJECTED -> VOIDED | DISPUTED}`, plus `EXPIRED`, `ABORTED_BY_HOST`, `HOST_LOST`, `INCIDENT`.

Numbered sequence (spec 6.1 and 6.3, with additions in brackets):
1. R local agent runs the mode selector (6.1). Chooses Hosted. UI shows "host sees the packet".
2. R Disclosure Compiler builds the Context Packet (full / derived / tokenized / handle-only items, canaries), byte-exact preview, excludes Pull-only items. [User approves the preview. Spec 6.2 says approval is "once per (digest, mode, lens, budget)"; for Hosted the approval object is not defined.]
3. [R asks the hub directory for hosts; hub returns host cards (key, price, claimed hardware, rep column).] R requests a quote from H via relay. H signs a quote with a cap. [Quote contents are not specified.]
4. Hub creates PayPal order `intent=AUTHORIZE` at the cap; requester authorizes (hold, 29 days, 3-day honor period for capture, per research/09).
5. R encrypts the packet to the host key (or enclave attestation key in Sealed) and sends via relay. [H must check the funds exist and the run token is valid before decrypt; not specified.]
6. H runs Cell + Sidecar under its own root, host-metered under the cap; model calls use a hub-issued per-task Nebius key with budget. [How H gets the pack, how the key is issued, how the hub meters: not specified.]
7. H returns encrypted result + host-signed receipt. R runs Result Guard and promotion rules; proposals go to Q.
8. Capture split author/host, Payouts to both after holdback; VOID path "when defense fires".

Failure transitions that exist in the spec: only "VOID when defense fires" and the canary spot-check mitigation. Everything below is missing.

## 3. Step-by-step failure analysis

Legend: F=fails, D=duplicated/repeated, O=out of order, C=concurrent, T=timeout, M=malicious actor, X=offline, S=state changed in between.

| Step | Question | Result |
|---|---|---|
| 1 mode select | M: prompt-injected local agent or a poisoned record mis-tagged `low` pushes data into a Hosted packet | Sensitivity comes from the extractor (an LLM, poisonable). Default for untagged items and `artifact: per file` is undefined. See F10. |
| 2 approval | S: lens grows between approval and next run; C: second device or double click | Approval keyed to lens, not bytes. See F2. |
| 3 quote | D: quote replayed for a second task; S: host key rotated, pack revoked, price changed; T: quote clock | Quote not bound to task. See F5, F11. |
| 3 directory | M: host with fake hardware claims, Sybil hosts, a host that only answers quotes | Hosted capability claims are unverifiable in Unsealed. See F12. |
| 4 authorize | T: 3-day honor period vs long tasks; F: capture later fails ("subject to risk and money availability", research/09); C: two authorizations for one task | See F5, F6. |
| 5 send | F: relay drops; D: replay; O: result arrives before ack; M: hub swaps host key; M: anyone with the public host key sends packets | See F3, F5, F11. |
| 6 run | M: host runs another pack/model; M: host reuses the Nebius key; X: host dies; M: host meters high | See F1, F4, F7, F12. |
| 7 return | F: result lost; M: garbage that passes schema checks; M: forged receipt; M: detector verdict forged | See F4, F6, F9. |
| 8 settle | C: capture vs timeout-void; M: requester rejects after reading result; D: capture retry; chargeback after payout | See F6. |

## 4. Consistency checks against other flows and the guarantee text

- 3.3 says Unsealed: "only the approved packet leaves your machine". But step 6 sends prompts (containing packet content) to Nebius under a key the hub issues, and the hub owns the Nebius account. B2 says "hub never gets vault content". If the hub, as account owner, can see request logs or content (UNVERIFIED either way; ZDR is account-level per architecture 3.2 B5), then "relay sees ciphertext only" and B2 are not the whole story. The text needs "the hub operator may be able to see prompts via its Nebius account unless ZDR plus a hub-side no-log property is verified" until proven otherwise.
- 3.3 and 6.3 say "host can read the packet" and "host can copy the pack", consistent. But 7.4 and 6.3 make the host the author of verdicts and receipts that also drive author-facing consequences (revoke proposal, payout freeze, reputation). That is a consistency hole (F9).
- 3.4 says receipts are "supervisor-generated". In Hosted the supervisor is the host's. The channel-schema argument (packs cannot write fields) holds against the pack, not against the host. The host can write any value.
- 5.4 says Hosted results are owner-attested and "cannot count as proof of isolation", but ranking uses "verified paid completion" and ratings from receipts. A host can mint completions (F4).
- 6.2 approval card "once per (digest, mode, lens, budget)" is incompatible with 6.3 step 2 byte-exact packet preview and with B3 "approved Context Packet only" (F2).
- 4.6 says Hosted has no vault capability, but manifest phases declare `work.memory.read: [tags]`. What serves `memory.search` on the host (a mini-index built from the packet) is not defined. Detectors D1-D4 (canary outside lens, enumeration) assume a lens larger than the data given; in Hosted everything the host holds is already disclosed, so those detectors have nothing to defend.
- Phase 15 exit test "Hosted run with cap and split capture" does not test any failure path above.
- Pull uses the requester's own Nebius key in the sidecar; Hosted cannot, so a payer for tokens appears that Pull never had. The pricing sections (5.2 `hosted_per_hour_usd`, 11.13 fee proposals) do not say who funds token cost.

## 5. Findings (ranked)

Severity key: critical = breaks a stated guarantee or loses money/data silently; high = realistic exploit or deadlock; medium = needs specific conditions.

### F1 (critical, abuse) Hub-issued per-task Nebius key lives on the hostile host, and who pays and who meters is undefined
Scenario: 1) R hires host H. 2) Hub mints a "per-task key with budget" and ships it to H so the sidecar can call Nebius. 3) H is root: reads the key from sidecar memory or env. 4) H uses it for its own inference jobs, sells it, or runs the key to the budget limit on every task, all billed to the hub account. 5) If Nebius cannot create ephemeral keys with a hard spend cap and revocation via API, the "per-task key" is in practice a long-lived account key (per-key budgets/ZDR/revocation are not in our primary-source digests, architecture B5 itself says per-key ZDR is not documented; UNVERIFIED). 6) At void/timeout nothing revokes the key, so a zombie run keeps spending. 7) Token cost appears in no quote, cap or capture formula, so the hub fronts it with unbounded exposure. 8) The host also self-reports token-count buckets in the receipt that determine what it charges.
Where: 6.3 step 5, 3.4 receipt, B5.
Fix: Do not ship any Nebius credential to a host. Run a hub-side model gateway: host sidecar talks to the hub gateway with a per-task bearer token (signed, bound to quote id, expires at hub time, killable instantly); the hub holds the only Nebius key, meters tokens itself, enforces the cap before forwarding, and stops forwarding on void. Add token cost as an explicit line in the quote: cap = host fee + author fee + hub-metered token cost, all inside the authorization. State in the guarantee that the hub gateway can see Hosted prompts (acceptable for Unsealed where the host sees them anyway; for Sealed the gateway must terminate TLS inside the enclave or this becomes a Sealed-mode contradiction, in which case Sealed uses a hub-signed Nebius key delivered only to the enclave via KMS with PCR condition and the hub still meters via Nebius usage per key, UNVERIFIED availability).

### F2 (critical, contradiction) Approval is not bound to the exact packet, the host key, or the run; failover and standing approvals disclose without consent
Scenario: 1) Spec 6.2 gives one approval per (digest, mode, lens, budget). 2) User approves a Hosted run once; the vault changes (new records match the lens, or a poisoned record is promoted). 3) Next Hosted run sends a packet built under the old approval, bytes the user never saw. 4) Separately: H1 goes silent mid-run; an automated retry re-dispatches the same packet to H2 (the spec has no failover rule). Now two untrusted hosts hold the data and the card never named a host. 5) A double click or two devices create two concurrent runs, two holds, two hosts.
Where: 6.2 step 2, 6.3 steps 2-5, B3.
Fix: For Hosted the approval object is (packet SHA-256, host key id, quote id, cap, expiry), signed on the phone or desktop, single use, no standing approvals, no auto-approve. Host change, packet byte change or cap change forces a new card. Dispatch is refused by R unless the signed approval matches the bytes being encrypted. Idempotency key per task id; the hub rejects a second AUTHORIZE for a live task id. Record "disclosed to" per packet in the audit log so the user can see exposure after a host vanishes.

### F3 (high, abuse) Hub controls the host key directory, so "relay sees ciphertext only" is only as true as the hub's honesty; key rotation and sender authentication undefined
Scenario: 1) R fetches host H's public key from the hub directory (the only anchor). 2) A compromised or curious hub replaces it with its own key. 3) R encrypts the packet to the hub's key; hub decrypts, re-encrypts to H, relays; neither side notices. 4) Also: the host key is public, so anyone can drop sealed-box packets on H's queue (unfunded spam, or a replay of a captured ciphertext). 5) Host key compromise or rotation after quote: the quote names key K1, packet goes to K2, or old ciphertexts decrypt for the leaked key.
Where: 3.2 B2/B3, 6.3 step 4; relay research/08 (sealed-box request noted as weaker: sender not authenticated; crypto_box sender can forge).
Fix: Host identity key published as a signed entry in the transparency log (the log exists, phase 11); R pins the host key on first hire and verifies an inclusion proof; key changes need a delay and show a requester alert. Packet envelope: ephemeral-static X25519 plus signature by R key, AAD = (task id, quote id, packet hash, host key id, hub run token), so H verifies sender, funding and binding before decrypting. Hosts also sign their result with the same key. In Sealed, the key comes only from the attestation document verified client-side (that part is already in the spec; make the Unsealed path say it is hub-trusted for key authenticity and list that in the guarantee).

### F4 (high, abuse) The host is the only meter and the only receipt author; billing inflation, fake completions, garbage-that-passes and wrong blame
Scenario: 1) Quote: cap $6 per hour, hosted per hour. 2) H runs 10 minutes of work, reports "duration bucket 55-60 min" and a high token bucket in a host-signed receipt. 3) Hub (which cannot see the host's clock or work) captures against the cap; requester pays near cap. 4) Alternatively H returns plausible filler that satisfies `schema_valid` and `citations_present` (the example acceptance checks are cheap to satisfy). Auto-accept rules capture. 5) H and a pack author (same person) use a funded requester account to loop paid runs and mint verified paid completions; the host-signed receipt supplies all "evidence". 6) H silently runs a cheaper model or a different pack than declared; the output is bad; the rating lands on the pack author. 7) Ranking says "Hosted results are owner-attested", but ratings and completions still feed ranking.
Where: 3.4, 5.4, 6.3 steps 5-7, 5.2 commercial.
Fix: (a) Hub-side token metering from the model gateway (F1) is the primary meter; time-based pricing is dropped for Hosted or measured from hub-observed signed events (run start/finish messages through the hub) not host reports. (b) Cap is hard in the gateway and in the PayPal authorization. (c) Receipt fields: tokens and cost come from the hub, only host-attributable fields (verdict enum, duration) come from the host and are labelled; the hub countersigns what it observed. (d) Hosted outcomes accrue to a (pack, host) pair: failures attribute first to the host; pack rank only counts Hosted runs from hosts in good standing, and Hosted completions are weighted zero for pack rank until certified by the hub's own Certifier hosts. (e) Acceptance checks for Hosted need a content-quality check (known-answer sub-tasks inserted by R's compiler, see F8) not only schema checks. (f) Wash-trading rule: no same-owner or same-payment-instrument links between host, author, requester; minimum non-refundable fee stays.

### F5 (high, gap) Quote and authorization are not bound to the task; the host cannot verify funds; honor-period and over-cap behavior undefined
Scenario: 1) H signs "cap $6" with no task id, packet hash or expiry. 2) A requester replays the quote for a larger job, or H later claims "packet is larger than quoted" after decrypting (it only learns size after decrypt) and demands more or aborts after reading the data. 3) R sends the packet before H has proof that an AUTHORIZE exists; H runs on credit, then the authorization fails, was voided, or exceeded. 4) A long job passes the 3-day capture honor period; reauthorize gives a new authorization id (research/09), the old signed token is stale. 5) Capture at the end fails ("subject to risk and money availability"), H worked for free; learning this, hosts either stop serving new requesters or demand prepayment, defeating escrow.
Where: 6.3 steps 3-4; PayPal digest.
Fix: Quote = hub-co-signed object (task id, requester key, host key, pack digest, packet size bucket and max bytes, model, price per unit, cap, expiry in hub time, nonce). The packet envelope must include the hub-issued run token proving AUTHORIZE succeeded (hub checks status, not R). Host rejects before decrypt if token invalid; once H decrypts and then aborts without result it earns nothing and takes a reputation strike (the packet has already been exposed, say so in the UI). Host cannot exceed the packet size bucket. Reauthorization is a hub-internal operation with its own signed progress events, never needing the requester online. For the capture-failure risk: take an up-front partial capture (a small "start" capture as host deposit) or use CAPTURE intent into hub balance with refund of the remainder; document the loss of the VOID story for that portion.

### F6 (high, race) Settlement races, lost results and free-riding on rejection
Scenario: 1) H finishes, uploads the encrypted result; the relay drops it (or TTL expires). R sees timeout and the hub VOIDs; H did the work and gets nothing. 2) Opposite order: R clicks Accept at the same instant the timeout VOID fires: capture fails after void, or void fails after capture and R re-dispatches (double paying). 3) R downloads the result, reads it, clicks Reject, hub VOIDs. Requester got the work free; repeated at scale kills supply. 4) Split capture: capture happens once; the allocation between author and host when only one of them failed (host garbage, pack fine) is undefined; "VOID when defense fires" punishes both. 5) 180-day dispute window (research/09) with payouts made after short holdback: requester disputes with PayPal after payout; the hub is merchant of record and eats the loss. Hub also holds customer funds, a regulatory topic (UNVERIFIED, not researched).
Where: 6.3 step 7, 6.2 payment text.
Fix: One hub-side per-task state machine with conditional writes (DynamoDB conditional update or equivalent): CAPTURE and VOID are mutually exclusive transitions; every PayPal call carries an idempotency key per (task, transition) (PayPal request-id header is believed to exist, UNVERIFIED in our digests; confirm). Two-phase delivery: H first posts a signed commitment (result hash, size) to the hub; R retrieves until ack; if R never retrieves within the TTL, funds settle per the commitment rules (host paid minus a stake) so a lossy relay does not equal VOID. Reject only for objective failed checks or a dispute opened with evidence; otherwise auto-capture after the review window, at which point R must hold the result sealed (decrypted only after Accept for paid-for-result tasks, or accept a small non-refundable work fee). Define the split table: host-fault, author-fault, requester-fault, and indeterminate each with fixed shares. Holdback sized by risk and by seller stake/reputation rather than a flat 180 days.

### F7 (high, failure-mode) Host vanishes or stalls mid-run: no heartbeat, no dead-man rule, no revocation of the key, no deletion story, no resume
Scenario: 1) H accepts, receives the packet, goes silent. R's UI shows "running" until the user cancels. 2) Hold stays open 29 days; capture honor period passes. 3) H may be a slow-loris, sending content-free "progress" ticks forever while billing time. 4) The Nebius key (F1) stays valid; the zombie run keeps spending. 5) The packet is on H's disk indefinitely; there is no deletion attestation possible in Unsealed. 6) R retries on another host (F2). 7) Pull has checkpoints and rollback; Hosted has none, so a 4-hour job lost at hour 3 restarts from zero.
Where: 6.3, 7.4 (only defense-fire is specified).
Fix: Hub-observed liveness: H must post signed heartbeats with strictly monotonic counters through the hub; missing N heartbeats moves the task to HOST_LOST, kills the hub gateway token, voids unspent hold, strikes the host. Hard wall-clock and token caps enforced by hub. Heartbeat progress must be tied to gateway token usage (a host with no model calls for T minutes is stalled unless the pack declares tool-only phases). Offer resumable steps: the Hosted task is a sequence of hub-visible phases (plan/work/return); partial results land per phase so one host failure does not lose all. Say plainly that data exposure cannot be undone and there is no deletion proof in Unsealed; keep a per-packet "disclosed to hosts" ledger. Auto-failover is off by default (F2).

### F8 (high, abuse) Canary spot-check tasks are distinguishable from real tasks, and they do not detect copying
Scenario: 1) Hub sends known-answer tasks from hub-owned requester accounts. H sees: new requester pubkey with no history, always the same PayPal payer/payment instrument or the hub as buyer, synthetic packet content (low entropy, template-like, uniform PII shapes, no tokenization quirks), packet sizes and arrival times that cluster, relay source IP/connection pattern, no phone-approval signature timing, same task shapes repeated. 2) A cheating host (lazy, inflating, or copying data) behaves honestly on tasks that fail a "looks real" classifier and cheats on the rest. 3) Even perfect indistinguishability only catches lazy or overcharging hosts: a host that quietly copies packets passes every known-answer test. Tripwire canaries only fire if the host uses the stolen value somewhere the hub watches (honeytoken beacons); a careful thief never does. 4) The spot-check budget: who pays for the fake tasks, and does the hub capture real money on them (distinguishing signal: the payer)?
Where: 6.3 "Remaining Hosted gap" paragraph.
Fix: State the claim honestly: spot checks measure host quality and billing honesty, not confidentiality. For indistinguishability: use pooled real requester accounts with history (opt-in "verification sponsor" requesters whose real tasks are replaced or whose spare real tasks are sampled for shadow execution), real payment instruments, packets generated by the same Disclosure Compiler from synthetic vaults with realistic distributions, randomized timing and size, and the same approval path. Have R's compiler add small known-answer sub-tasks and per-task honeytokens (unique per host per task, backed by beacon URLs/email-style tokens the hub monitors) inside real packets, so every real task is also a probe; the user sees them in the byte-exact preview (labelled as decoys in the preview, not in the packet). Report the detection probability per host as the column, with the assumption written down. Note a host can pre-scan plaintext for decoy patterns; treat honeytokens as detection of careless misuse only.

### F9 (medium-high, contradiction) Host-attested verdicts drive author-facing consequences; incident suppression and framing are both open
Scenario: 1) Suppression (spec admits): host's supervisor reports `verdict=clean` regardless. 2) Framing: a rival host or the author's competitor operates a host that reports D2 "canary in outbound" with a signed evidence bundle against a competing author's pack. Per 7.2 a deterministic CRITICAL executes revoke, "signed revocation proposal to hub", payout freeze, and reputation effects, all from data the host fabricated. Anti-framing rule 7.3 requires supervisor-signed canary placement, but the supervisor is the host. 3) A requester colluding with a host reports an incident after receiving the result to get VOID and keep the work.
Where: 7.2, 7.3, 7.4, 3.4.
Fix: In Hosted, an incident report from the host is evidence about the host-pack pair; it may void that run and downgrade the host-pack pair, but it must not by itself revoke a pack globally, freeze other payouts, or touch author reputation. Revocation of the pack requires Certifier reproduction (re-run the pack on a hub host with the evidence fixtures). Host-signed evidence carries a "host-claimed" tag in every UI. Hosts that file incidents at a rate far above the population rate get a flag. Incident-driven VOID after result delivery needs the F6 dispute path.

### F10 (medium-high, gap) Hosted packet content is only as safe as the sensitivity tags, and tokenization can leak back
Scenario: 1) A record from a poisoned document was auto-classified `low` by the extractor, or a file artifact has no tag. 2) Mode selector, which relies on the lens sensitivity, lets it into a Hosted packet; the user, under approval fatigue, approves a long packet card. 3) Tokenization (Presidio) is reversible: the same token across runs lets H build a profile; pack output may carry tokens that R detokenizes into text that then flows into other local steps (tool arguments, another pack's packet), creating a path from foreign output to sensitive data placed in the next outbound message. 4) Free-text derived items may embed identifiers that the PII model misses.
Where: 6.1, 6.3 step 2, 4.1 sensitivity defaults.
Fix: Hosted packets are default-deny: only items with user-confirmed `sensitivity: low` (or explicitly user-selected per item) are eligible; `secret`, `high`, untagged and Q-tier never. Run a deterministic scanner (secret regexes, Presidio, entropy, known-identifier list from the vault) over the final bytes; any hit blocks unless the user overrides item by item. Per-task token mapping (fresh random tokens per run, no cross-run stability). Detokenized output is marked "contains sensitive data" and cannot be included in any outbound packet or tool call without a fresh Disclosure Compiler pass. Daily-digest style batching must not be used for Hosted approvals (F2).

### F11 (medium, undefined-behavior) Clock skew, ordering, replay and message binding are unspecified; Sealed has extra clock and rollback problems
Scenario: 1) Quote and run-token expiry use device clocks; R is 10 minutes slow and rejects valid quotes, or H is 10 minutes slow and accepts expired ones; per-hour billing uses H's clock. 2) Relay delivers the result before the "accepted by host" event, or twice; R processes result then a stale "running" state overwrites it. 3) A captured ciphertext packet is replayed to H (duplicate run, extra gateway spend if keys per task are reusable). 4) A result for task X is delivered into task Y's slot and Result Guard accepts it because nothing binds the result to the packet hash. 5) Relay TTL is measured by the relay clock, offline queue semantics conflict with forward secrecy (research/08). 6) Sealed: the enclave has no persistent storage, so a host restart resets in-enclave counters and caps; enclave wall-clock is obtained through the host parent instance (UNVERIFIED whether a trusted time source exists), so in-enclave expiry and rate limits are host-controllable and replay of the same ciphertext is possible unless the hub tracks used nonces.
Where: 6.3 steps 3-6, Sealed paragraph, relay design in research/08.
Fix: All expiries evaluated by the hub in hub time; tokens carry relative TTL plus hub-signed issue time and clients tolerate a bounded skew window, rejecting beyond with a clear UI. Ordering by per-task sequence numbers and a hash chain of protocol events (each message includes the hash of the previous), not by timestamps. Every envelope AAD = (task id, seq, direction, packet hash or quote id); receivers keep seen-nonce sets until expiry; idempotent handlers. Gateway tokens single-use per task. Sealed: counters and caps live in the hub gateway, not in the enclave; hub tracks used nonces; attestation freshness via a requester-supplied nonce.

### F12 (medium, gap) Pack provenance, host identity and memory behavior on the host are undefined
Scenario: 1) How H obtains the pack is never specified: for non-open IP tiers the author must hand the pack to H (so the host copy is authorised, a leak path nobody prices), for open packs H pulls by digest. 2) In Unsealed, D9 (pack drift) runs in H's supervisor; H can swap prompts, model or runner and still sign "digest sha256:..." receipts. The requester cannot check which model actually ran (quote says Nemotron; H routes to a cheaper local model). 3) Host listings claim "stronger compute" and uptime; there is no attestation or benchmark that binds claims to a box. 4) Sybil hosts after a ban: an account-age gate exists for authors, none for hosts. 5) `memory.search` and phases declared `memory.read` have no defined meaning in Hosted (4.6 says no vault capability), so pack behavior differs from its Pull certification: the certified score (per pack version, model, Pull sandbox) does not transfer to Hosted conditions, and the listing could still show the certified LCB.
Where: 5.2 manifest, 6.3, 4.6, 5.4.
Fix: Add a "Hosted pack distribution" step: only digest-pinned packs from the registry; for non-open IP tiers a per-host license (and a stated "host can copy" line on the author side too, not only the requester side). Host-reported model identity is verified by routing models only through the hub gateway (F1), so the host cannot substitute; host hardware claims shown as claimed unless measured by hub benchmark tasks. Hosts need a stake or identity cost. Define Hosted memory: the packet is staged as a read-only snapshot with the same `memory.search` interface served by the host broker; certification for Hosted is a separate (pack, model, mode) row; show the Pull LCB on Hosted listings only if a Hosted-mode certified run exists.

## 6. What is solid and should be kept
- Labelling three modes honestly, and excluding Pull-only items structurally from Hosted packets.
- Hub AUTHORIZE before dispatch, void on failure, capped authorization; fixed-schema author-bound channels.
- Treating the host as untrusted for everything except the declared packet, and running Result Guard on arrival.
- Owner-attested labelling, once it is carried through to author-facing consequences (F9).
