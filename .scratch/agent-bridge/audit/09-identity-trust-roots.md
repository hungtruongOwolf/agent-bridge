### 1.2 Numbered sequence (happy path, Pull) with trust-relevant state

1. **Author account creation.** Author registers at hub. State: hub account row, "account age" counter. Author key generated locally, public key registered. No identity proofing described.
2. **Pack publish.** `bridge pack sign`: author signs canonical digest. Hub Certifier runs pack on private suites in sandboxes on the hub. Hub countersigns an in-toto-shaped attestation bound to (digest, model, suite version). Entry appended to hash-chained log. Registry stores `card.json`.
3. **Requester account creation.** Requester registers; identity key generated; PayPal payer linked at purchase.
4. **Discovery.** Requester agent calls hub MCP (`browse_agents`), gets cards. It verifies: author signature, hub countersignature, "log inclusion", revocation status, license, tested_on, driver tier. State needed locally: hub public key (source: undefined), a revocation list (freshness: undefined), a log head (source: undefined).
5. **Approval.** Approval card for (digest, mode, lens, budget). Phone approval over relay. State: phone key (pairing undefined), approval record (validity period undefined).
6. **Run token + AUTHORIZE hold.** Hub issues "one-time run token" and a PayPal authorization. Token contents, binding, redemption point and expiry are not specified.
7. **Stage + mint capability.** vaultd stages snapshot. Broker mints Biscuit (root key location: Broker; rotation: not specified).
8. **Run.** Supervisor checks revocation "before every start and on each broker call". Pack runs; v3 adds workflow steps, checkpoints, per-step attenuation, human gates, retries, resume.
9. **Result, accept, capture.** Result Guard, acceptance, Accept. Capture, payout after holdback, signed content-free receipt "generated by the supervisor", sent to hub.
10. **Incident (alt path).** Detector fires, ladder runs, supervisor signs incident, proposes revocation to hub, PayPal VOID and payout freeze.
11. **Rating.** Requester posts 1-5 + reason code bound to a capture. Ranking recomputed "by anyone from the signed attestation log".

Hosted adds: host key lookup (source undefined), host-signed quote, E2E packet via relay to host key, host-run Cell, host-signed receipt, capture split.

Vault sharing: device enrollment (undefined), journal replication over relay with per-device keys, crypto-shred by dropping per-record key, tombstone hash in journal.

### 1.3 State machine for the one piece that is stateful and missing: the run lease

The design has "one-time run token" but no states. The minimal machine it needs (my proposal):

`ISSUED --(supervisor redeem, run_id, device)--> STARTED --(checkpoint n)--> STARTED --(finish)--> FINISHED --(accept)--> CAPTURED`
`STARTED --(crash)--> SUSPENDED --(resume same run_id, same digest, same engine major)--> STARTED`
`ISSUED|STARTED|SUSPENDED --(ttl)--> EXPIRED --> VOID`
`STARTED --(CRITICAL)--> KILLED --> VOID or HOLD`

Absent from v2 and v3. See F8.

## 3. Consistency check against other flows and the guarantees text

1. **3.2 B2 says "hub never gets vault content" and 3.4 says "Hub metadata: Counts and digests".** The hub is also registry, relay, run-token issuer and escrow. It therefore sees requester account + pack digest + timestamps + sizes + payer per run. "Counts and digests" understates this. Contradiction with the product's privacy framing (F10).
2. **3.3 guarantee text says "The author receives nothing during the run" but 3.4 Rating and Receipt channels go to the hub, which publishes rankings per pack.** The hub-to-author aggregate channel (per-pack counts, timing of paid completions) is outside the schema. A low-volume pack's author can infer a specific buyer by the timing of a rating (F10).
3. **5.4 "Anyone can recompute the ranking from the signed attestation log" versus requester privacy.** To recompute "distinct payers" a third party needs payer identifiers in the log. Either payer identifiers are public (hiring graph leaks, and GDPR erasure conflicts with append-only) or the ranking is not independently recomputable (F10, F11).
4. **5.3 step 10 "supervisors check before every start and on each broker call" versus Pull's privacy-first stance.** If check = hub call, every broker call tells the hub the run is still alive and from where. If check = local cache, freshness is undefined (F3, F10).
5. **4.5 crypto-shred ("journal keeps a tombstone hash") versus 4.2 journal line `content_hash`.** An unsalted hash of low-entropy personal data is confirmable and remains personal data. Contradiction between erasure claim and journal schema (F11).
6. **7.2 "signed hash-chained incident record" and 7.3 "canary placement and hit evidence are signed by the supervisor and log-verifiable".** Both rely on a signer who is the incentive-conflicted requester in the framing scenario. 7.3's anti-framing rule covers canary-only hits but not requester-fabricated egress/taint hits (F4).
7. **5.3 step 5: "hub countersignature on the certification"** is described as protection, but the Certifier is the hub's own component executing author code; a compromised Certifier host yields the countersign key (F1).
8. **v3 workflow checkpoint/resume (research-v3/02 section 8: engine version and workflow digest pinned in run, resume under different digest refused)** has no counterpart in the token/lease/revocation model: a resumed run must re-check revocation and the lease, and the design has no rule (F8, F3).
9. **6.3 step 3 and 5: "the model uses a hub-issued per-task Nebius key with budget"** versus 3.2 B5 / arch-harness-platform: "no per-key scopes or spend caps documented". Budget enforcement point is the host's proxy, i.e. the untrusted party (F12).
10. **Section 11 items 11 and 12 (who operates sealed hosts, root-key recovery) are listed as owner decisions but they are prerequisites for every key statement in 3.3.** The guarantee text for Sealed Hosted is not issuable until key directory and attestation-verifier hosting are decided (research-v2/09 open question: "where is the attestation verifier and revocation list hosted so the hub itself is not the single trusted party").

## 4. Findings (ranked)

Each finding: scenario, location in design, fix. Severity is my estimate.

### F1 (critical, gap/abuse): No defined root of trust; the hub is a single point of total compromise, and its signing key is reachable from the component that runs attacker code

**Scenario.**
1. Attacker publishes a pack and escapes the Certifier sandbox (author code runs in the hub's AWS account; B9 relies on separate pack/grader sandboxes, not on key isolation).
2. Hub signing material (countersign, log, revocation, run-token, quote keys; arch does not say they are in KMS/HSM) is read or used.
3. Attacker countersigns an attestation for a trojan pack digest, appends it to the log (same key), removes a real revocation from the list, and issues run tokens.
4. Every requester client accepts all of it because the verification chain ends at "the hub key" and no client-pinned root, key expiry, or independent witness exists.

Even without escape: a malicious hub operator or a stolen AWS admin credential gives the same result. The product promise is that the hub is "honest-but-curious" (B2) but every integrity property (countersignature, log, revocation, ranking) is hub-signed, so honest-but-curious is not what the integrity design needs.

**Where.** 3.1 hub box, 3.2 B2, 5.3 steps 4-6, 5.3 step 10, 7.2 step 6.

**Fix.**
- Key hierarchy: offline root key (hardware token, ceremony documented, 2-of-3 holders) signs short-lived (30 day) online intermediate keys with distinct roles: attestation, log, revocation, run-token, relay directory. Root public key is compiled into the client and into released supervisor builds; rotation by root-signed key-rollover statement with overlap.
- Role keys live in KMS/HSM in a separate AWS account from the Certifier fleet. The Certifier produces an unsigned result blob; a tiny signer service (separate account, no inbound path from Certifier except a schema-validated queue) signs it. Certifier IAM role can never call `Sign`.
- Compromise runbook: root-signed "all intermediates before T revoked" statement; clients refuse attestations signed by intermediates older than the rollover.
- Separate trust: author signatures stay authoritative for "this digest is what the author published"; the hub countersignature is only "this digest passed suite S". State this in the guarantee text.

### F2 (critical, gap): Our own TCB (supervisor, sidecar, vaultd, Disclosure Compiler) has no signed, transparent, reproducible release path; the hub could ship it; upstream SHA pins do not establish trust

**Scenario.**
1. Requester installs `bridge` once, and the app auto-updates from the hub (or from an npm/pip package we publish).
2. A hub compromise (F1), a maintainer's stolen npm token, or a poisoned dependency of the Disclosure Compiler (Presidio, libsodium wrapper, Biscuit WASM) ships a build whose supervisor ignores the revocation list or whose compiler adds extra items to staged bytes while the preview shows the clean set.
3. Supervisor, vaultd and Disclosure Compiler all run on the requester machine with vault access. All pack-isolation guarantees evaporate silently.

Separately: "upstream pinned by SHA" (manifest `provenance.upstream[{repo, sha}]`) is self-declared by the author. A SHA pin freezes content but says nothing about whether the content was reviewed. A pack importing a malicious upstream at a pinned SHA passes "pinned upstream refs" validation (5.3 step 2). Also, if the upstream repo is deleted or force-pushed, the pin becomes unfetchable and the author may vendor a different copy. (Git object-ID hash function details for SHA-1 repositories: UNVERIFIED here; do not rely on SHA-1 pins for security.)

**Where.** 3.5 build list, 5.2 `provenance`, 5.3 step 2, section 8 (all our crypto and policy libraries are third-party deps).

**Fix.**
- Release signing key for the TCB separate from every hub key, root-signed per F1. Client refuses unsigned or non-logged builds.
- Binary transparency: each release hash appended to the transparency log (with F5 properties). Client checks inclusion before install and on every update.
- Reproducible builds for supervisor, sidecar, Disclosure Compiler, vaultd; CI publishes the build recipe; a second party (or the owner's second machine) rebuilds and cosigns.
- No auto-update of the TCB; update shows a diff summary and needs a local confirmation. Lockfiles with hashes (not tags); vendored, audited dependency set for the crypto and compiler path; `npm`/`pip` provenance and 2FA-enforced publish.
- Upstream pins: the hub (not the author) fetches the pinned SHA at publish time, mirrors the tree into the content-addressed pack, and the manifest records the tree hash (SHA-256) in addition to the Git SHA. Digest covers vendored content. Reject packs whose pinned upstream cannot be mirrored.
- Define what "pinned upstream" does and does not claim in the guarantee text: "content is fixed", not "content is safe".

### F3 (high, undefined-behavior): Revocation has no freshness, no fail mode, and no anti-rollback; hub outage or network block decides between "revoked packs still run" and "Pull is bricked"

**Scenario (fail open).**
1. Pack P is flagged malicious and revoked at 10:00. Requester's laptop is offline (plane) or an attacker on-path blocks the hub (the hub URL is fixed, so a captive network can).
2. Supervisor "checks before every start": its cached list pre-dates 10:00. With no `valid_until` it treats the list as valid forever.
3. Requester runs P over private data; revocation is never seen. A mid-run `broker call` check also hits the cache.

**Scenario (fail closed).** If implementer chooses to fail closed on a failed fetch, a hub outage disables all private-data Pull runs, including an in-flight multi-hour workflow at its next broker call; DDoS on the hub becomes a way to kill every active run.

**Scenario (rollback/freeze).** A hostile network or hub serves an old signed list with a valid signature. No monotonic sequence number is checked.

**Scenario (revocation abuse).** Hub or a requester-reported incident (F4) revokes honest packs; there is no appeal timer on automatic revocations and no separation of "revoked for compromise" from "deprecated".

**Where.** 5.3 step 10, 6.2 step 1, 7.2 step 6.

**Fix.**
- Signed list format: `{seq, issued_at, valid_until, entries[{digest|author_key|measurement, reason_class, effective_seq}], prev_list_hash}`. Supervisor stores the highest `seq` seen in a local append-only store and rejects lower ones.
- Policy by sensitivity of the lens, shown on the approval card: lists up to 24 h old are fine for medium; high-sensitivity or secret-adjacent lens requires list age under 1 h or a successful fetch at start (fail closed with an explicit "run anyway with weaker guarantee text" for low-sensitivity only). In-flight runs: if list freshness expires mid-run, pause at the next step boundary (workflow checkpoint) rather than kill; resume when fresh.
- Distribution redundancy: list pushed through the relay and mirrored on a second origin (static bucket + a witness); short-lived "revocation epoch" counter in each run token so a hub that cannot be reached still cannot be pinned to an old epoch for longer than `valid_until`.
- Local denylist (7.2 step 5) always wins and is never overwritten by the hub list.
- Revocation reasons: `compromised-key`, `malicious-behaviour-confirmed`, `deprecated`, `dispute-hold`. Only the first two block runs on their own; others warn. Automatic holds expire unless a human-reviewed confirmation lands.

### F4 (high, abuse): Requester-held supervisor signs the evidence the hub uses to void payments, freeze payouts, revoke packs and score safety; a malicious requester can get free runs and frame competitors

**Scenario.**
1. Attacker S creates 20 requester accounts (F9) and runs a competitor's pack C or any author's pack over a seeded, fake "private" lens.
2. S's own supervisor (S holds the key; Pull runs on S's machine) places a canary in the result path itself, or simply emits `{detector: D2, verdict: CRITICAL}` signed with its own key. The 7.3 anti-framing rule (canary alone never hurts reputation) is bypassed by also emitting a fake egress/taint record, which is just another signed supervisor field.
3. Hub receives "CRITICAL incident"; per 7.2 it VOIDs the open authorization (S keeps the result, pays nothing), freezes the payout, and proposes revocation. Repeated across sybil accounts, C's pack is revoked and its ranking shows "safety incidents".
4. Also flips: the receipt's "detector verdict enum" and "acceptance result enum" (3.4) are requester-attested, so S can mark honest packs as failed to claim refunds (`refund: acceptance_checks`).

Hosted has the same problem with the host as attester ("owner-attested", 7.4), but there at least the label is honest. For Pull the label should be "requester-attested" too.

**Where.** 3.4 receipt, 7.2 money step, 7.3 anti-framing, 5.4 "safety incidents" column.

**Fix.**
- Treat all supervisor-signed fields as requester claims in the hub's model. Void/freeze/revoke on a claim is a temporary hold only (payout holdback exists), not a verdict.
- Verification: incident evidence must include a replayable event history (v3 section 8) with the detector inputs; hub or Certifier re-executes the engine against recorded model/tool responses and checks the detector fires (this audits supervisor logic, not model behaviour). Use redacted histories (Disclosure Compiler) and consent per incident, since histories contain private data.
- Requester-side economics: refundable deposit or stake per requester that is burned for confirmed-false incidents; per-requester incident-claim rate limit and a "claim accuracy" score; new-account claims weigh near zero.
- Safety-incident ranking column counts only hub-reproduced incidents.
- Void limits: if the pack delivered a result (the requester accepted or the Result Guard passed), a VOID after the fact should be a dispute, not a void. Capture the portion for work done up to the first detector hit.
- Receipts: drop requester-attested enums from the ranking path unless corroborated.

### F5 (high, gap): The "transparency log" is a single-writer hash chain: no inclusion/consistency proofs, no witnesses, no monitors, so split-view and silent rewrite are undetectable

**Scenario.**
1. Hub (or an attacker with the log key) keeps two chains: the public one, and a private one containing a trojan attestation for pack digest D served only to Victim V's client. The chain is a linear hash chain; V can only verify the part V is shown.
2. V's check "log inclusion" (6.2 step 1) passes against the chain V is served. Nobody else sees the divergence because no client compares heads, and there are no third-party monitors.
3. Equally, the hub may rewrite old entries (alter a certification score LCB) and re-sign forward: a linear chain with one signer has no external anchor.
4. Monitors: nobody is assigned to watch for "key K signed something unexpected" (author-side monitoring) or "digest D countersigned without a Certifier run". Without monitors, a log is only a database.

**Where.** 5.3 step 5, 3.1 "Transparency log (Ed25519 + hash chain)", 5.4 "anyone can recompute".

**Fix.**
- Use a Merkle tree log with signed tree heads and inclusion/consistency proofs (RFC 9162 shape) rather than a linear chain; or integrate an existing log (Rekor/Sigstore is already named as the upgrade path; UNVERIFIED whether public Rekor is suitable for private pack metadata). Do not describe it as "transparent" until at least one external witness cosigns heads.
- Witness cosigning: 2+ independent witnesses (our own second AWS account does not count; a university or community partner, plus an owner-run witness) cosign heads; clients require a cosigned head newer than N hours and store the last head for consistency checks.
- Clients gossip head hashes through the relay (cheap) so split views are detected.
- Author-side monitor in Pack Studio: polls the log for any entry naming the author key or pack id; email/push on unexpected entries. Hub-side monitors: alert on certifications without a matching Certifier run record.
- Until that exists, the listing must say "hub-attested; no independent witness".

### F6 (high, abuse): Key directories (host key, phone key, device keys) are served by the same hub that relays; first contact and pairing are unauthenticated, so the "relay sees ciphertext only" claim fails against a malicious hub; queued sealed boxes have no forward secrecy

**Scenario A (host key substitution).**
1. Requester picks a Hosted pack. The host's static key is delivered in the hub's listing (6.3 step 4: "E2E-encrypted ... to the host key").
2. A compromised hub (or a malicious host impersonation with a re-registered key) swaps in its own key. Requester encrypts the Context Packet to it. Relay = hub = reads the packet. Noise IK (08-relay) assumes the initiator already has the responder's authentic static key; first contact has none.

**Scenario B (phone pairing).**
1. User pairs a phone PWA by opening a URL (path unspecified in v2). If the pairing code or key exchange passes through the hub, the hub registers its own device key as "phone".
2. The hub can now sign approvals for any approval card (the approval card is rendered on the phone from hub-relayed data, so even the "byte-exact preview" is hub-controlled).
3. Approval replay: the design approves "once per (digest, mode, lens, budget)" with no expiry, and the lens is a query, so a later run under the same approval stages different bytes.

**Scenario C (queued sealed box).** 08-relay admits offline queueing with a sealed-box request has no forward secrecy. A host key theft later decrypts all queued and archived packets (the relay may archive ciphertext).

**Scenario D (device enrollment).** New vault device enrollment is undefined; a hub-in-the-middle can enroll a device and receive replicated journal ciphertext plus wrapped record keys.

**Where.** 3.2 B3, 6.3 step 4, 4.6, 08-relay lines 41-44 and 59-61.

**Fix.**
- Pairing: out-of-band authenticated channel (QR on screen showing the public-key fingerprint, scanned by phone; or SAS comparison of 6 words) never routed through the hub. Same for adding a vault device. Device list is a signed membership log held by the user's own devices, not the hub.
- Host and author keys: published in the F5 log; requester client pins on first hire (TOFU) and shows a loud warning on change; the approval card displays a short fingerprint. For first contact, require host key inclusion in a witnessed head (F5).
- Approval record binds `hash(card bytes, staged-lens-bytes-hash, run_id, nonce, expiry)`, expiry <= 24 h or per-run; re-approval if the staged byte hash differs from the approved preview hash (the supervisor compares, not the UI).
- Host prekeys: signed one-time/medium-term X25519 prekeys with 24 h validity, deleted after use (X3DH-shaped); hosts rotate and relay deletes ciphertext after TTL.
- Relay learns less: see F10.

### F7 (high, gap): Author key loss, compromise, rotation and recovery are undefined; hub countersign gives a stolen key extra credibility

**Scenario.**
1. Author A's laptop is infected; the Ed25519 key in `~/.bridge/keys` is stolen (private key location in Pack Studio is not specified).
2. Attacker signs `acme/finance-analyst 1.0.2` with the stolen key. A trojan that behaves on the Certifier's private suites (not on the real lens; pack can distinguish synthetic data) passes certification, receives the hub countersignature, appears in the log, and requesters who auto-follow patch versions inherit it (diff re-approval exists but approval fatigue is noted as open in 4.8).
3. A cannot revoke its own key: no key-revocation message type exists, only digest revocation; A cannot prove which versions were signed by the attacker versus A. The attacker backdates a signature timestamp to before the compromise window.
4. Opposite case: A loses the key; their 4.8-rated top pack can never be patched; a new key means a new identity with zero reputation (ranking is per pack id, but who owns `acme/`?).

**Where.** 5.3 steps 5-6, 5.1 digest, 7.2 revoke (digest only), section 11 (no key recovery decision for authors).

**Fix.**
- Key roles: author root key (offline, rarely used) signs author release keys (yearly); release keys sign packs. Key-rollover statements signed by the root go in the log; a hardware key or OS keychain is required (`bridge pack sign` refuses file keys unless `--insecure`).
- Time authority is the log's inclusion time (witnessed STH), never the signature's own timestamp. Key revocation = log entry `{key, compromised_since}` signed by author root or by hub after a 7-day dispute window with email + second-factor confirmation; supervisors refuse all digests first included in the log after `compromised_since`.
- Cooling period for permission-widening MAJOR bumps (7 days visible in log before Pull runs may use them) and "publish notification" to the author's registered contacts (so the real author sees an unexpected release in time).
- Recovery: a pre-registered recovery key (paper) can sign a rollover; without it, hub-assisted recovery requires identity re-verification and a 14-day delay, announced in log. Namespaces are owned by an author-root key, not by hub account.
- Certifier gap: the Certifier must also run a "behaves differently on real-looking vs synthetic data" test; declare what certification does and does not prove.

### F8 (high, race/undefined-behavior): Run token, lease and clock semantics do not survive long workflows, crash-resume, concurrency or hostile clocks; Pull metering is not enforceable by anyone but the requester

**Scenario.**
1. Long v3 workflow starts; hub issues "one-time run token" and AUTHORIZE hold.
2. At hour 5 the engine host crashes and the workflow resumes from checkpoint 14. The token was consumed at start. Either resume is refused (the user loses 5 hours of paid work and the hold lapses) or the implementer allows token reuse, after which the same token funds unlimited re-runs and double starts.
3. Two supervisors on two of the user's devices (journal replication is multi-device) start the same task from the same token concurrently. No lease holder exists; both write into U's journal under the same task id; CAS conflicts at the vault, not at the lease.
4. The payment authorization has a finite honor period (PayPal specifics UNVERIFIED here; confirm in PayPal docs: honor period vs validity; reauthorization limits). A multi-day workflow with human gates outlives it; capture then fails after the author has done the work.
5. Clock: Biscuit expiry and revocation `valid_until` use the local wall clock. Requester sets the clock back to keep an expired capability or stale revocation list alive; in Hosted the host chooses the clock for receipts and quotes. Time drift between phone, relay and supervisor makes approval expiry ambiguous.
6. Pull metering: the supervisor that "redeems" the token is requester-controlled and the pack is fully visible to the requester (5.6). A requester can rerun the pack locally with no token. The token protects the requester's escrow, not the author's revenue. The "revenue per run" owner incentive (section 1) is therefore honor-based for open Pull packs.

**Where.** 6.2 step 3 and 9, v3 section 8 (checkpoint resume), 4.6 multi-device, product sentence.

**Fix.**
- Define the lease state machine in section 1.3: `run_id` (UUIDv7) minted by the requester, hub token = signature over `{run_id, requester_key, digest, mode, cap_usd, issued_at, lease_ttl, epoch}`; redeem is idempotent per `(run_id)`; one active holder device id; heartbeat extends the lease via the relay (lease renewals tolerate offline up to a bounded grace); resume by the same device or after lease expiry with a fresh `lease_seq`; the hub accepts capture only for the highest `lease_seq` once.
- Checkpoint record carries `{run_id, lease_seq, workflow_digest, engine_major}`; resume re-verifies revocation freshness (F3) and capability, mints new Biscuits per step.
- Payment: split long runs into milestones with separate small authorizations (re-authorize at checkpoints, human gate between) and set the authorization lifetime from the workflow's declared max duration; refuse workflows whose declared duration exceeds it.
- Time: signed hub time in every response (`X-Hub-Time` signed with the role key); supervisor tracks max hub time seen and uses a monotonic clock for in-run expiry; wall-clock skew over 5 minutes shows a warning; replay protection by nonce + expiry on every hub-signed object.
- Honesty: state in the pack listing that Pull revenue depends on license terms, updates, certification and convenience (open tier), and that the token is not DRM. Align section 1's incentive sentence.

### F9 (high, abuse): Account creation and sybil resistance are one phrase ("account-age gate", "payer-diversity weighting"); ranking, certification cost and namespace squatting are all cheap to attack

**Scenario.**
1. Attacker registers 200 requester accounts with PayPal sandbox/personal identities (arch-harness-platform risks note: "wash trading and Sybils with sandbox PayPal identity"). Each buys the attacker's own pack once at the minimum fee. The cost is the platform fee (10-15% of the fee, per section 11 proposals) times volume, which is trivial next to the ranking and "verified paid completion" gain. Payer diversity is counted per account, which the attacker multiplies at will.
2. Attacker submits 10,000 packs to the Certifier; each runs Nemotron tokens (section 11 item 7: who pays certification tokens is undecided). Result: cost denial of service on the hub.
3. Attacker registers `acme-finance`, `acme/finance-analyst`, `acme/finance-analyst-pro` clones with similar cards (typosquatting, as with ClawHub's 341 malicious skills noted in 5.3). Namespaces have no owner binding beyond "first account".
4. An attacker waits out "account age", then uses the account.

**Where.** 5.3 step 6, 5.4 "wash-trading rules", section 11 items 7 and 14.

**Fix.**
- Certification budget: per-author monthly quota; paid certification (deposit refundable on pass) or sponsor-funded tokens; queue limits; reject duplicates by digest similarity.
- Identity tiers shown on the card: unverified pseudonym, verified domain (DNS TXT with author key fingerprint), verified payer (PayPal identity), verified org. Ranking weight depends on tier. Namespace policy: `owner/name` where `owner` is bound to a key or domain; confusable-name rejection.
- Wash resistance: cap per-payer influence (diminishing returns), weight payments by payer funding-source age and distinct funding source (not account), discount payer/author pairs with graph overlap (same IP ASN, same device cluster, same funding source), delay ranking credit until the dispute window ends, and publish ranking with and without verified-paid weight.
- Rating requires an accepted run with minimum captured amount; ratings from accounts with fewer than N runs on other authors are discounted.
- Document the residual: sybil resistance is economic, not absolute.

### F10 (high, contradiction/abuse): The hub sees the full hiring graph with IP, timing and size; the guarantee table says "counts and digests"; the "recompute ranking" claim and the privacy claim conflict

**Scenario.**
1. Requester R, with a sensitive task (medical, legal, HR), browses `browse_agents`, fetches card for `acme/divorce-lawyer-helper`, requests a run token, relays packet or result sizes, and later rates. Hub holds `{R account, IP, payer identity, pack digest, timestamp, duration bucket, token bucket, cost, outcome enums}` for each run, and (if relay carries v3 workflow events or approval round trips) message sizes and timings that correlate with data volume.
2. Hub is honest-but-curious by assumption (B2) and a breach leaks the graph. The pack author, who gets "nothing during the run" (3.3), still sees timing-correlated aggregate ranking updates (F10 contradiction 2) and can infer a low-volume buyer.
3. The update check ("Pack id and version query only") reveals installed packs and cadence to the hub.
4. Recomputable ranking needs payer-distinctness proofs in a public log; that makes the hiring graph public or the claim false. And an append-only public log makes erasure (F11) impossible for any identifier that sits in it.

**Where.** 3.2 B2, 3.3, 3.4 last row "Hub metadata", 5.4, 6.2 steps 3 and 9, 08-relay "Relay learns metadata only (who talks to whom, sizes, timing)".

**Fix.**
- Rewrite 3.3/3.4 honestly: "The hub learns: your account, which packs you view/hire, when, the price, size and timing buckets of relay messages, the outcome enums. It does not learn vault or result content."
- Reduce collection: download the whole card index (or signed delta) and browse locally; fetch pack contents by digest from a content-addressed mirror/CDN with no account header; run token via blind-signed tokens or a pre-purchased token pool (Privacy-Pass style, UNVERIFIED applicability) so the hub cannot link run to account for non-paid flows; pad relay frames to size classes and send fixed-rate keepalives for high-sensitivity runs; offer Tor/proxy support for hub calls.
- Ranking: publish per-pack signed aggregates plus per-payer unlinkable commitments (HMAC with hub secret and per-pack salt) so third parties verify counts and consistency over time but cannot link payers across packs; state that payer distinctness is hub-attested, not third-party recomputable. Alter 5.4 and the "anyone can recompute" claim accordingly.
- Delay and batch rating/receipt delivery with random jitter so the author cannot correlate timing with a known buyer.

### F11 (high, contradiction/gap): Erasure, crypto-shred and audit/journal design conflict; vault key hierarchy and device revocation are undefined; audit-log signing key is on the same host as the sandbox it audits

**Scenario (erasure).**
1. User exercises right to erasure (GDPR Art. 17, applies to us as the controller of hub account data and to the user's own vault if we process it; applicability of household exemption to the vault itself: UNVERIFIED legal question, get counsel).
2. `crypto-shred` drops the per-record key on device A. Device B was offline and still holds the key and ciphertext; the relay holds queued journal envelopes; backups hold both. Shred is effective only after every replica processes it.
3. The journal keeps `content_hash` and "tombstone hash". For a low-entropy value (phone number, diagnosis, name) a hash is guessable and therefore still personal data; erasure is not achieved.
4. The sidecar audit log (hash-chained, signed) holds memory queries and lens items (search queries contain user data); v3 event histories hold private data (v3/02 line 220 acknowledges they "need the same protection as the vault" but sets no deletion path). Embedding indexes (SQLite/vector) retain information derived from the record.
5. Hub-side: author identity, payer identity, receipts, ratings sit in a public append-only log (F10): cannot be erased.

**Scenario (key hierarchy).** Per-record `key_id`, per-device keys, vault root key: wrapping relationships not specified. If record keys are wrapped to each device, revoking a lost device cannot recover keys it already holds; a thief with the device and the unlocked OS user can decrypt all. Root-key recovery undefined: lost laptop + phone = vault gone, or a recovery path (hub escrow?) re-creates a hub trust root.

**Scenario (audit signing).** Supervisor, sidecar log writer and key live on the requester machine. A Cell escape (shared-kernel container on WSL2 is explicitly flagged as feasible risk) lets the pack read the signing key, truncate the chain from the point of its own activity and re-sign forward. `bridge audit verify` passes. Also the Biscuit root: if long-lived and shared across runs, an escaped pack gets it.

**Where.** 4.2 journal line, 4.5 crypto-shred, 4.6 multi-device, 4.10, section 11 item 12, 3.1 supervisor/audit log, v3/02 section 8.

**Fix.**
- Journal and logs hold commitments, not content hashes: `content_commit = HMAC(record_key, content)`, and `record_key` is the thing shredded. After shred the commitment is not confirmable. Audit-log payloads (queries, lens items) are encrypted under per-run keys with the commitment in the chain; erasure drops the run key and the chain stays verifiable.
- Key hierarchy: user root key (recovery phrase, offline) -> vault master -> per-namespace keys -> per-record keys; devices hold namespace keys wrapped to a device key; device removal rotates namespace keys and re-encrypts forward (old data a stolen device already read cannot be recalled; state it). Shred = broadcast signed erase message through all devices; erase is "complete" only when all enrolled devices ack or are removed; show status.
- No hub escrow of root key by default; offer optional social/paper recovery; document the loss mode.
- Index and embeddings: tagged by record id, deleted on shred; rebuild from journal for others.
- Hub: keep personal identifiers out of the append-only log (pseudonymous ids, no email, no payer identity); personal data in a deletable database; document retention. Relay TTL on ciphertext (08-relay lists TTL).
- Audit/supervisor key: forward-secure sealing (key evolves per entry and old keys are deleted, FSS-style: UNVERIFIED on exact library) and periodic anchoring of the chain head to a second location the Cell host user cannot write (phone via the paired channel, or the F5 log in coarse form). Supervisor, vaultd and sidecar run as a different OS user from anything the Cell's driver can reach; key in OS keystore/TPM-backed where available. Biscuit root key: per-run ephemeral, in Broker memory only, never persisted, so no rotation story and no cross-run exposure.

### F12 (medium-high, abuse): Hosted mode lets the untrusted host hold and spend a hub-issued Nebius key whose budget only the host's own proxy enforces; Hosted receipts and quotes bind nothing to the hub

**Scenario.**
1. Hub issues the host a per-task Nebius key "with budget" (6.3 step 5). arch-harness-platform and 3.2 B5 state per-key spend caps and scopes are not documented (UNVERIFIED here; check Nebius Token Factory docs). The budget therefore lives in the host's proxy (host root).
2. Host extracts the key from its own process and burns arbitrary tokens, including reselling inference. The hub pays. Detection: Nebius account-level usage spikes, after the fact.
3. In the same account, the hub's single Nebius account also has the ZDR setting (3.2 B5); if all requesters' prompts and all hosts' keys sit under one account, one key leak or hub compromise affects all and links prompts across requesters at Nebius.
4. Host-signed receipts and quotes: the hub trusts host key bound to host account; a host can sign a quote with a hostile cap or falsified duration and the requester sees only a host-signed number. Spot-check canary tasks (6.3 end) catch only some behaviour.

**Where.** 6.3 steps 3, 5, 6, 7, 3.2 B5.

**Fix.**
- Do not give hosts a Nebius key. Hub-operated inference proxy: host calls `hub-inference` with a short-lived, per-task, token-bucket-limited credential; the hub holds the Nebius key and enforces budget, rate and model class server-side; requester prompts at hub are visible to the hub (state it) unless E2E to Nebius is feasible (UNVERIFIED).
- Alternatively the requester pays Nebius directly with the requester's own key placed in the packet (visible to host: rejected) or use a per-requester Nebius sub-account if Nebius supports it (UNVERIFIED).
- Per-task keys from separate Nebius projects/keys so revocation is granular; rotate on any host incident.
- Quotes: hub-countersigned caps (hub verifies host limit against listing), receipts reconcile with hub-side proxy meter, not host-reported meter.
