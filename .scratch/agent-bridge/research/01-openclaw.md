# 01 - OpenClaw as base platform

Researched 2026-10-07. Method: `git clone --depth 1 https://github.com/openclaw/openclaw` (HEAD committed 2026-10-06, package version 2026.9.8) and read README, VISION, SECURITY and `docs/` in the repo (these are the source of docs.openclaw.ai); `gh api` for repo metadata and advisories. Nothing was run or installed; all behavior claims are from docs/source text, not tested.

## Summary

OpenClaw is a very large, MIT-licensed, TypeScript, local-first personal-agent platform (about 391k GitHub stars, foundation-stewarded, NVIDIA and Amazon listed as partners). One long-lived Gateway per host owns channels, sessions, tools and a WebSocket control plane. It has a rich plugin SDK (channels, providers, agent harnesses, tools, hooks, HTTP routes, services), MCP client and server support, an A2A 1.0 channel, a "Reef" E2E-encrypted agent-to-agent relay channel, node pairing for remote machines, and sandbox backends (Docker, SSH, OpenShell).

Verdict: build agent-bridge as a set of OpenClaw plugins (marketplace/relay/payment/observability) plus a small external relay/registry service. Do NOT depend on OpenClaw for the thing it explicitly disclaims: hostile multi-tenant isolation inside one Gateway. For the "stranger runs a task on my machine" step, use one isolated Gateway cell (container) per delegated task or per requester, which OpenClaw's own docs recommend. Also: OpenClaw already ships much of what we planned to build (A2A, Reef, node host, sandbox, MCP, voice, approvals), so the differentiator must be marketplace + ranking + payment + isolation story, not transport.

## Key facts (with sources)

Identity, license, maturity
- License MIT; language TypeScript; created 2025-11-24; latest release v2026.9.8 (2026-10-03); pushed 2026-10-07. Source: `gh repo view openclaw/openclaw` (https://github.com/openclaw/openclaw), LICENSE.
- Stars 391,525 at query time (same source). Stewarded by the OpenClaw Foundation, a 501(c)(3); partners listed include Amazon, GitHub, Microsoft, NVIDIA, OpenAI (docs/start/why-openclaw.md, https://docs.openclaw.ai/start/why-openclaw). Security maintainers include NVIDIA and Tencent engineers (SECURITY.md).
- Project's own maturity scorecard: overall 68%, "Alpha" band (quality Alpha 65%, completeness Beta 71%) (docs/maturity/scorecard.md, https://docs.openclaw.ai/maturity/scorecard). Plugin APIs are all "experimental" (docs/plugins/building-plugins.md); "Fleet" multi-tenant is experimental (docs/gateway/multi-tenant-hosting.md); agent harness SDK is experimental (docs/plugins/sdk-agent-harness.md).
- Install: Node 24.16+ or 26.1+; `npm i -g openclaw@latest`, `openclaw onboard --install-daemon`; installers for macOS, Linux, Windows (README; Windows paths in docs/platforms/windows.md: native CLI/Gateway, WSL2, node mode).

Architecture
- Gateway: single daemon, typed WebSocket API (default `127.0.0.1:18789`), also serves HTTP on the same port; TypeBox schemas; clients (CLI, Control UI, TUI) and nodes connect over WS (docs/concepts/architecture.md, https://docs.openclaw.ai/concepts/architecture).
- Pairing: every WS client has a device identity, new devices need approval, gateway issues device token, connect must sign a challenge nonce. Remote access: Tailscale/VPN or SSH tunnel (same doc).
- Channels: 20+ messaging channels (README). Channel = plugin (`api.registerChannel`).
- Skills: SKILL.md folders, per-agent allowlists, ClawHub registry (docs/tools/skills.md, docs/concepts/multi-agent.md).
- Plugins: native plugins ship `openclaw.plugin.json` manifest and can register providers, CLI backends, speech, media, search, channels, tools, hooks, background services, HTTP routes; "bundle-style" plugins (skills + MCP servers + config, also Codex/Claude/Cursor bundle layouts) are the preferred low-risk form (VISION.md; docs/plugins/architecture.md; docs/plugins/manifest.md). Install from ClawHub, npm or git (docs/tools/plugin.md). ClawHub = "Skill + Plugin Registry for OpenClaw", MIT, ~9.5k stars (`gh repo view openclaw/clawhub`).
- MCP: client (`mcp.servers`, stdio / SSE / streamable HTTP, per-session tool deny) (docs/tools/mcp.md); server mode `openclaw mcp serve` exposes channel conversations (docs/cli/mcp.md); node-hosted MCP servers and skills published from a paired node (docs/nodes/mcp-and-skills.md).
- Multi-agent: multiple isolated agents per Gateway, each with own workspace, agentDir, auth, sqlite sessions, routed by bindings; but workspace is "the default cwd, not a hard sandbox" without sandboxing (docs/concepts/multi-agent.md). Sub-agents via `sessions_spawn`, own session per run, configurable nesting, own model (docs/tools/subagents.md). Also swarm, workboard (Control UI boards/cards with run history; extensions/workboard).
- Agent harness: "harness" in OpenClaw = low-level executor of one agent turn (e.g. Codex app-server), registered by trusted/bundled plugins via `AgentHarnessV2`; not our "harness pack" meaning. Our notion (prompt + tools + MCP + skills) maps better to an OpenClaw agent entry (workspace files AGENTS.md/SOUL.md, skills allowlist, tool policy, MCP servers, model) (docs/plugins/sdk-agent-harness.md, docs/concepts/multi-agent.md).
- Model providers: bundled `nvidia` provider (NVIDIA-hosted OpenAI-compatible API, `NVIDIA_API_KEY`) (extensions/nvidia/README.md). Custom providers with custom base URL are documented (docs/concepts/model-providers/custom-providers.md; content not read in detail), so Nebius Token Factory should be configurable as a custom OpenAI-compatible provider. UNVERIFIED: not tested with Nebius; no Nebius provider plugin exists in `extensions/`.

Reaching another machine/agent (three existing paths)
1. A2A channel (bundled plugin `a2a`): publishes public Agent Card at `/.well-known/agent-card.json`, accepts authenticated A2A 1.0 JSON-RPC `SendMessage`/`GetTask` at `/a2a/v1` with per-peer bearer tokens, per-peer rate limit (default 30/min), one skill per exposed agent, `exposeAgents` filter, outbound to configured peer URLs (`a2a:<peer>`). Each peer+contextId gets its own isolated session, never the operator's main session. Limits: text only, no streaming, no file transfer, `CancelTask` refused (no abort seam). (docs/channels/a2a.md, extensions/a2a/README.md.)
2. Reef channel (bundled plugin `reef`): E2E-encrypted (Ed25519/X25519) agent-to-agent messaging through a relay (public `https://reefwire.ai`; protocol/relay source `openclaw/reef`, MIT, 6 stars, last push 2026-09-25), friend codes and safety-fingerprint pairing, fail-closed guard LLM on outbound (DLP) and inbound (prompt-injection) with owner review queue, autonomy tiers (notify-only / bounded 3 replies per day / extended 12 per hour), hash-chained local audit. Inbound content is untrusted, command-unauthorized, URLs inert. (docs/channels/reef.md.) This is a near-identical sibling of agent-bridge's relay + E2E + audit design but oriented to chat between friends, with a mandatory OpenAI/Anthropic guard model (UNVERIFIED whether a Nebius/NVIDIA guard can be pinned: docs show only `openai` or `anthropic` providers).
3. Node host: headless `openclaw node run` on a second machine connects to a Gateway over WS with `role: node`; gateway forwards `system.run`, node-published MCP tools (`mcp.tools.call.v1`) and skills; exec approvals enforced on the node; node capability approval is a separate gate (docs/nodes/node-host.md, docs/nodes/mcp-and-skills.md, docs/gateway/pairing.md). Direction is the reverse of what we need for a marketplace: a node lends its tools to a Gateway the node owner trusts; the Gateway runs the model. Useful for "my GPU box / my dataset host", not for "stranger's whole agent".
- Also: Cloud Workers (`openclaw connect --ephemeral`, Crabbox provider) dispatch session work to throwaway machines with transcript staying on the Gateway (docs/gateway/cloud-workers.md); Beam and Session Share share sanitized session snapshots between Gateways (extensions/beam, extensions/session-share).
- HTTP APIs on Gateway: OpenAI-compatible `/v1/chat/completions`, `/v1/responses`, `/tools/invoke`, admin HTTP RPC. All documented as FULL operator access when using the shared token; keep on loopback/tailnet only (docs/gateway/openai-http-api.md, tools-invoke-http-api.md, extensions/admin-http-rpc/README.md).

Security model and known issues
- Stated trust model: one trusted operator boundary per Gateway; "not designed as a shared multi-tenant boundary between adversarial users on one gateway"; "Anyone who can operate an agent can make it do anything that agent can do"; session ownership/visibility are usability features, not security boundaries (SECURITY.md; docs/gateway/multi-tenant-hosting.md).
- Their recommended isolation for untrusted tenants: one full Gateway "cell" per tenant via `openclaw fleet` in hardened Docker/Podman containers, own state, token, loopback-only port; Fleet is experimental, Linux/macOS tested, Windows untested; outbound egress unrestricted by default (Podman `--network internal` can block it); OAuth tokens stored plaintext in SQLite state; host/operator is trusted (resistance to compromised host is a non-goal) (docs/gateway/multi-tenant-hosting.md).
- "Prompt injection without a policy/sandbox/tool boundary bypass" and "malicious plugin after a trusted operator installs it" are explicitly not treated as vulnerabilities. A malicious native plugin equals arbitrary code execution in the gateway process (SECURITY.md; docs/plugins/architecture.md line ~890).
- Sandbox: off by default; tool execution only moves into Docker/Podman/SSH/OpenShell/Crabbox/MXC when enabled; docs say "not a perfect security boundary". Gateway process always stays on host (docs/gateway/sandboxing.md). NVIDIA OpenShell is supported as a sandbox backend (docs/gateway/openshell.md); NVIDIA "NemoClaw" distribution hardens OpenClaw with OpenShell (docs/start/why-openclaw.md, cites NVIDIA press release). Nebius publishes an OpenClaw security hardening guide (https://nebius.com/blog/posts/openclaw-security, linked from same doc, not read by me).
- Published GitHub security advisories: 500 returned by `gh api repos/openclaw/openclaw/security-advisories?state=published` (paged to 5 pages x 100; 255 high, 220 medium, 25 low; count may be capped by my 5-page limit; none counted as critical in that data). Examples 2026-09-11: GHSA-3mq7-q27j-mq7q "Exec approvals could outlive their reviewed working directory" (high), GHSA-vhpg-cq3w-v8p9 "OpenAI-compatible transport could send provider credentials to the wrong endpoint" (medium). Sources: `gh api` on https://github.com/openclaw/openclaw/security. This shows an active fix cadence and also a large attack surface.
- Third-party ClawHub skill/plugin supply-chain risk: docs say malicious or blocked community releases are refused on install and arbitrary npm/git/local sources need `--force` non-interactively (docs/cli/skills.md, docs/tools/plugin.md). UNVERIFIED: any specific malware incident counts; I did not search external reporting.

Payments / marketplace hooks
- No payment, billing, or marketplace feature found in core docs or `extensions/` (grepped for paypal/x402/payment; only unrelated hits). `extensions/radius` is a model-credit gateway provider, not a marketplace. ClawHub is a registry for skills/plugins, free, no pricing.
- Extension points where our layer can attach: (a) channel plugin (`api.registerChannel`) for a "bridge" channel; (b) tool plugin to expose `delegate_task`, `browse_agents`, `pay`; (c) plugin HTTP routes and background services in the Gateway; (d) hooks (tool-result middleware, plugin permission requests `plugin.approval.*` for owner approval prompts routed to chat/phone UI; docs/plugins/plugin-permission-requests.md); (e) MCP server config (static MCP servers declared in plugin manifest); (f) A2A Agent Card as discovery format for listings; (g) Control UI plugin surfaces: Workboard plugin shows plugins can add navigation pages, dashboard widgets and session accessories (extensions/workboard/README.md); (h) diagnostics-otel / diagnostics-prometheus plugins for observability events (extensions/ directory listing; docs/gateway/opentelemetry.md not read).

## Fit for agent-bridge

Good fit
- Reuse instead of build: Gateway runtime, agent loop, skills, MCP client, sub-agents, cron, channels (so a requester can use WhatsApp/Telegram/voice front-ends), A2A protocol and Agent Card for listings, Reef pattern (E2E, guard, audit) as design reference or even transport, exec approvals, sandbox backends including NVIDIA OpenShell (good Nebius x NVIDIA story), NVIDIA provider plugin, Control UI + Workboard for polished long-task visibility, voice-call/talk plugins.
- "Owner publishes agent+harness": an OpenClaw agent entry (workspace + skills + MCP + tool policy + model) is already a portable-ish definition; we add a `listing` manifest (price, speciality, A2A Agent Card skills).
- A2A already gives authenticated task submission with per-peer session isolation and async `returnImmediately` + `GetTask` polling, good for long tasks.

Gaps / mismatches
- OpenClaw's trust model assumes the operator trusts the agent's code and the people talking to it. Our marketplace requires three-way distrust: requester vs third-party harness, owner vs requester, relay vs both. OpenClaw does not provide this inside one Gateway; we need cell-per-task (container, no egress except model endpoint and approved tools, ephemeral state, destroyed after the task) and result-only return. Fleet cells and OpenShell give building blocks but are experimental.
- Reverse isolation problem (requester info vs third-party harness): OpenClaw's own tooling does not address it. Practical design implied by the docs: send only a minimal task package (no ambient memory; A2A sessions per peer/context are already separate from main session; use a fresh agent entry with memory plugin disabled), run the model call through requester-chosen endpoint where possible, and treat the owner's harness as untrusted code from the requester's side. This is an agent-bridge design problem, not an OpenClaw feature. Needs follow-up research (confidential compute / attestation is outside this topic).
- A2A plugin: text only, no streaming, no files, no cancel, bearer-token trust per peer (pre-shared), not suitable as-is for anonymous marketplace counterparties; Reef is closer but its relay is a third-party service with signup and an OpenAI/Anthropic guard requirement.
- Node host direction (gateway borrows remote tools) is inverted vs marketplace delegation.
- Plugin API is experimental and the project moves fast (calendar versions, doctor migrations); pin a version.
- Size/complexity: huge codebase (175 bundled extension dirs); onboarding and Windows host support need checking on our two demo machines. Windows Fleet/cell isolation is untested per docs; Docker Desktop on Windows is the likely path. UNVERIFIED.

Can we build agent-bridge as an OpenClaw plugin? Yes for the owner-side and requester-side logic: one native plugin (channel `bridge` plus tools plus Control UI page plus approval hooks plus a manifest-declared MCP server) distributed by npm/ClawHub, with the registry, ranking/stars, relay, payments (PayPal sandbox) and attestation outside OpenClaw as a small service (can sit on AWS). The execution sandbox for foreign tasks should be a separate OpenClaw cell (container) launched by our plugin, not the owner's main Gateway. Sitting only "beside" OpenClaw would waste its channels/UI/skills; building purely inside it would couple multi-tenant security to a boundary it disclaims. Hybrid is the recommendation.

## Recommendation

1. Use OpenClaw (pin v2026.9.8 or newer tested tag) as the agent runtime and UI on each machine; do not fork core.
2. Build `agent-bridge` as an external plugin package (channel + tools + Control UI page + approval flow) plus a thin hosted registry/relay service (listings, ratings, stars, escrow with PayPal sandbox, optional AWS hosting).
3. Executing foreign tasks: spawn an ephemeral hardened container cell (Fleet-style or OpenShell sandbox, read-only mount of one granted folder, egress allowlist to Nebius endpoint + approved tools, no owner credentials) and return only the result after owner preview. Prove the isolation in the demo (raw file never appears on requester machine, requester secrets never visible to owner harness).
4. Reuse A2A Agent Card format for listings and A2A JSON-RPC semantics for task lifecycle; study/reuse Reef (`openclaw/reef`, MIT) for E2E, fingerprint pairing, guard and audit chain rather than writing crypto ourselves.
5. Configure Nebius Token Factory as a custom OpenAI-compatible provider (base URL) with an NVIDIA Nemotron model so the Nebius x NVIDIA requirement holds; verify early (untested).
6. Observability: start from OpenClaw diagnostics (OTEL) and Workboard before adopting munder-difflin.

## Risks

- Alpha maturity (68%), experimental plugin SDK and Fleet; breaking changes across fast releases.
- Security claims: OpenClaw disclaims multi-tenant isolation; our marketplace's central promise would rest on our own container-cell design. A single escape or misconfig breaks the pitch. Large advisory history (hundreds of published advisories, mostly high/medium).
- Prompt injection and malicious third-party harness are out of OpenClaw's threat scope; guard LLM classifiers (Reef) are probabilistic, not guarantees.
- Plaintext OAuth tokens in state dirs; egress unrestricted by default; sandbox off by default.
- Windows hosts: Fleet untested; demo machines may be Windows (the owner's machine is Windows 11); budget time for Docker/WSL2 setup.
- Scope creep: OpenClaw is huge; polish/demo time is limited (Nebius deadline 2026-10-30, 23 days).
- Name/brand: our judges may see "wrapper around OpenClaw"; differentiate with marketplace, ranking, payment, isolation proof.
